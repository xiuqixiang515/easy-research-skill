# 冲突检测精度研究（v6）

日期：2026-10-25　|　起点：`v1.5.0`（`3cf932b`）　|　产物：`v1.6.0`（`f1f46de`）、`v1.6.1`（`a96d0ba`）、`v1.6.2`（`fc8df49`）
问题：昨天刚上的「口径冲突」到底能不能用？在真实规模的库上会不会把用户淹掉？

## 0 结论

1. **v1.5.0 的判据不可用**。120 张卡、12 个项目、150 组真冲突的库上，端到端 **查准率 0.125、查全率 0.167**——它报了 200 条（撞上限），其中只有 25 条是真的；同时还有大量真冲突没排上号。
2. **改成「项目优先 + 剔除通用标签」后，同一基准上 P=1.000 / R=1.000**（v1.6.0）。
3. **v1.6.0 自己留了一个召回漏洞**：当一组卡片的标签组合几乎一致时，所有标签都会被判成"通用"，整组漏报（5 组探针只剩 2 组）。v1.6.1 补了"标签无区分力时不剔除"的判据，回到 5/5，基准不变。
4. 阈值不敏感：剔除线取 0.3–0.5 之间结果一致；0.2 会把项目标签也当通用（查全归零），0.6 会放过真正的通用标签（查准掉到 0.120）。

## 1 基准怎么造

`harness/conflict_bench.py` 生成 120 张卡：

- 3 个学科 × 4 个项目 × 10 张卡
- 每个项目有专属标签（楼A、队列A、日志…）、一个通用标签（节能、预测、复现）、一半卡片再加"方法"标签
- 6 个项目在中途改了口径（功能单位、边界、t0、验证范围、种子、切分各一组），其余保持不变
- 真值由构造直接给出：**同一项目、同一字段、取值不同 = 150 组**

同时生成两个版本：带 `项目` 字段、不带 `项目` 字段，用来比较"有没有显式项目"的差别。

## 2 四种判据

| 判据 | 规则 |
|---|---|
| v0（≈v1.5.0） | 同学科 + 任意共同标签 |
| v1 | 同学科 + 共同标签，剔除学科内出现频率 ≥θ 的标签 |
| v2 | 有 `项目` 时按项目比；缺字段时退回 v1 |
| v3 | 同 v2，但学科内卡片 <5 张时不做剔除 |

## 3 结果

### 3.1 离线（直接对真值打分）

| 判据 | 查准 | 查全 | F1 | tp / fp / fn |
|---|---|---|---|---|
| v0 | **0.072** | 1.000 | 0.135 | 150 / 1925 / 0 |
| v1 (θ=0.4) | **1.000** | 1.000 | 1.000 | 150 / 0 / 0 |
| v2 | 1.000 | 1.000 | 1.000 | 150 / 0 / 0 |
| v3 | 1.000 | 1.000 | 1.000 | 150 / 0 / 0 |

θ 扫描（v1）：0.2 → R=0；0.3/0.4/0.5 → P=R=1；0.6 → P=0.120。

### 3.2 端到端（跑真实 `weekly`，解析表格）

| 版本 | 判据 | 报出 | 查准 | 查全 |
|---|---|---|---|---|
| v1.5.0 | 同学科 + 共同标签 | 200（撞上限） | **0.125** | **0.167** |
| v1.6.0 | 项目优先 + 通用标签剔除 | 150 | **1.000** | **1.000** |
| v1.6.1 | 同上 + 标签无区分力时不剔除 | 150 | **1.000** | **1.000** |
| v1.6.2 | 同上 + 索引与配对提速 | 150 | **1.000** | **1.000**（0.159 s）|

v1.5.0 的两个问题叠在一起：**噪声（92.8% 是误报）+ 上限截断（真冲突排到 200 条之外）**。

### 3.3 5 组矛盾的验收探针

| 版本 | 检出 |
|---|---|
| v1.4.1 | 0 / 5 |
| v1.5.0 | 5 / 5 |
| v1.6.0 | **2 / 5**（回归） |
| v1.6.1 | **5 / 5** |

v1.6.0 漏掉的 3 组在医学：6 张卡标签完全一样（`conflict, synthetic`），被判成"通用标签"后没有任何共同标签可用，于是整组跳过。修法是：一个学科内标签组合 ≤2 种时，标签本来就没有区分力，此时不做剔除。

## 4 我自己犯的两个测量错误

1. **真值用错了字段**：第一版 `truth()` 用「项目」字段判断"是否同项目"，而对照数据集故意不带这个字段，导致全部 120 张被当成同一个项目（真值 2950 组，正确是 150）。改成从构造处带一个内部标记。
2. **解析错了表**：端到端解析最初扫全篇表格，把「卡片一览」的 `学科/类型` 列当成了卡片 ID，凭空多出 1 个误报。改成先切出「口径冲突」小节再解析。

两处都写在报告里，因为它们和外一个教训是同一类：**测量工具本身也会错，而且往往错在"看起来对"的地方**。

## 4.5 规模测试：2000 张卡时周报 12.7 秒

基准库只有 120 张卡，看不出规模问题。另造 2000 张卡（40 个项目 × 50 张、42 个标签）测周报：

| 版本 | 耗时 | 冲突行数 |
|---|---|---|
| v1.6.1 | **12.707 s** | 200（撞上限）|
| v1.6.2 | **0.273 s** | 200（撞上限）|

定位过程：先把「学科」去掉（跳过冲突检测）仍是 8.97 s，再把「标签」清空降到 0.27 s——**慢的不是冲突检测，是周报原有的「交叉组合线索」**：它对每个标签对做组内两两扫描，42 个标签就是 861 个标签对 × 最多 2000 张卡的两两比较。改成"每个标签对只取只带 ta 和只带 tb 的首张卡"后线性化，并加了 50 条上限。

顺带把冲突检测的候选索引也改成跳过通用标签——原来 `节能` 这种标签会把 2000 张卡两两配对（约 200 万对），只是被上限挡在输出层之外。

26 个探针里的 P20 没发现这个问题，因为它的 2000 卡夹具只有 3 个标签。**这是"探针覆盖不到真实形态"的又一例。**

## 4.6 我自己犯的第三个错误

改 `cross_tag_suggestions` 时，我用"从 `def cross_tag_suggestions` 切到 `def weekly_report`"的方式替换，把夹在两者之间的 `CONFLICT_KEYS`、`_generic_tags`、`conflict_rows` 一起删了，运行时报 `NameError: conflict_rows is not defined`。

教训很直白：**按函数名切片替换，必须确认被删区间里没有别的函数**。已按原逻辑（含两处优化）补回并重跑全部测试。

## 5 设计取舍

- **精度优先**。宁可漏，不可淹。用户会因为 1900 条误报直接关掉这个功能；漏掉的冲突在下次填了「项目」后会被补上。
- **`项目` 字段是主路径**。填了它，比较范围就是确定的，不依赖标签质量。模板已加 `- 项目:` 一行，文档写明"建议填，它决定比较范围"。
- **通用标签剔除是有条件的**：学科卡片 ≥5 张、标签组合 ≥3 种、频率 ≥40%，三条同时满足才剔除。少一条就不剔除，避免小库误伤。
- **不自动改数据**。只列并存，不判断哪个对——冲突的裁决需要领域判断，工具不该越界。

## 6 局限

- 基准是合成库，标签"干净"（专属标签不跨项目）；真实库的标签会更脏，精度可能低于 1.000。
- 120 张是精度基准，2000 张是性能基准；两者不是同一个库，精度在 2000 张上未测（只测了不崩、不超时）。
- 没有真人使用测试：不知道用户看到 150 条冲突时会怎么处理。
- 真值只覆盖"同一项目内改口径"，没覆盖"跨项目本应统一但没统一"这种情况。

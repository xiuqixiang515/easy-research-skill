# 淬炼想法：从直觉到可执行的假设

## 本文目录

适用：用户已经有一个模糊想法，需要判断它是不是真问题、值不值得做。

## 第一步：让用户自己复述

优先让用户用自己的话说明观察、推测与做法。若用户已经讲清楚，复用现有内容，不要求重说；若贴了摘要或代码，指出它不能替代用户对研究问题的解释。可用以下问题补足：

- 你观察到什么现象/遇到什么具体困难
- 你猜原因是什么
- 你打算怎么做

复述不清通常是两种原因：想法确实还空，或者想清楚了但表达欠组织。两种情况都值得先理一遍。

## 第二步：补全五段式

| 段位 | 问题 | 常见缺失 |
|---|---|---|
| X 场景 | 在什么数据、什么条件下？ | 只说"实际场景"，没有边界 |
| Y 方法 | 具体做什么操作？ | 只说"用深度学习"，没有机制 |
| Z 问题 | 要解决的核心困难是什么？ | 和 X 混在一起，说不出"难在哪" |
| 好在哪里 | 和谁比、好多少？ | 只说"更准确"，无对照 |
| 可推翻 | 什么结果证明它错？ | 几乎没有人为这一步设计过 |

五段补齐后，读一遍：**能不能想象出一个具体的实验场景？** 如果读完脑子里还是没有画面，说明还停留在概念层。

## 第三步：四问检验

### Q1 这个问题真实存在吗？

追问："谁在什么时候会因此受损？"

- 能说出具体的人、具体的任务、具体的代价 → 通过
- 只能说"这很重要""领域热点" → 不通过，回到现象观察

**判定标准：** 如果这个问题不存在，也不会有任何实际后果，那它就不是问题，只是不完美。

### Q2 现有方法为什么失败？

追问："失败机制是什么？"

- 能说出机制（"因为 X 假设不成立，所以在 Y 情况下失效"）→ 通过
- 只能说"性能不够""还不够好" → 不通过

**判定标准：** 好的失败机制解释，天然蕴含了解决方向。如果你不知道为什么失败，你的方法就是碰运气。

### Q3 我的方法为什么能解决它？

追问："是因果关系还是相关性？"

- 机制能对上：Q2 的失败机制 → 我的方法正好绕开/补偿它 → 通过
- "因为 A 方法在别的地方有效，所以在这里应该也有效" → 事后归因，风险高

**判定标准：** 可以用一段"如果……那么……因为……"说明机制；复杂时再画因果图。若机制仍是猜想，标为待检验假设。

### Q4 什么结果会让我放弃？

追问："什么实验失败，你就承认这个想法不对？"

- 能给出明确的、可能发生的失败判据 → 通过
- 说"应该不会失败"或"失败了可以再调" → 不通过

**判定标准：** 这一问是区分"科研"和"工程调参"的分水岭。设计不出失败条件的想法，做下去只会无限期延长。

## 第四步：最小验证实验

目的不是做完研究，而是**用最小成本拿到"支持 / 不支持 / 信息不足"的信号**。

必须写清五项：

| 项 | 要求 |
|---|---|
| 数据 | 用哪个公开数据集/已有的哪批数据，为什么它足以验证假设 |
| 对照 | 至少一个可信对照；计算类研究优先用当前强基线，实验/临床/工程类按领域选空白、安慰剂、历史或标准做法 |
| 指标 | 一个主指标 + 一个辅助指标，说清阈值 |
| 判据 | 预设什么结果算支持、什么算不支持、什么情况只能判为信息不足 |
| 耗时 | 预计多久，依赖哪些资源、排队、审批或培养周期 |

设计原则：

- **优先在最小规模上验证机制**，而不是在最大数据集上刷分
- **先跑通负对照**（把新模块关掉/空白对照），确认流程本身没问题；无法设置负对照的研究写明原因
- 以计算类研究为例：原型验证若需 2 周以上，通常说明切得不够小。培养、老化、寿命、季节代表性、临床随访等研究的等待周期由现象本身决定，不能为缩短对话而压缩、跳过或虚构完成

## 第五步：风险与退路

给出评级并写明退路：

| 风险 | 表现 | 退路 |
|---|---|---|
| 假设不成立 | 最小实验信号为负 | 退到"分析型"工作：解释为什么不行，这本身可以成文 |
| 别人做过了 | 检索发现高度重合 | 转为对比/复现+改进，明确差异点 |
| 数据拿不到 | 权限、伦理、规模 | 换公开数据集或合成数据，先说清局限 |
| 效果不显著 | 提升在噪声范围内 | 若子条件在实验前已预设，可按该范围下结论并标注范围；若看到结果后才挑出子组，只能标为**探索性发现**，说明多重比较，并另做独立验证，不能当作已验证的有效性 |

## 最终产出

一张 idea 卡，写入素材库：

```markdown
## 标题
一句话说清做什么

- 来源: 用户想法 / 文献 / 观察
- 问题: Z
- 现有做法: ...
- 短板: Q2 的失败机制
- 可延伸方向: 如果成功，下一步做什么
- 一句话: 在 X 场景下，用 Y 解决 Z，比 ……，能被 …… 推翻
- 标签: tag1, tag2
- 风险: 高/中/低
- 最小验证: 数据/基线/指标/判据/耗时
```

## 给用户的反馈原则

- 先准确复述有材料支撑的优点，再指出缺口；不预设用户想法有固定比例正确。
- **不要直接说"这个不行"**，要说"在什么条件下它会失效"，把判断权交回去。
- **不要替用户补全他没说的部分**。缺哪段就问哪段，不要脑补成"他大概是这个意思"。
- **最多给 2 个替代方案**。给多了等于没给。
